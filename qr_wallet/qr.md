# SolClub QR Payment Flow

## 1. QR GENERATION LOGIC

- The QR image is created by the Python `qrcode` library in `qr_wallet/qr_generator.py`.
- The generator builds a URL string, passes it to `qrcode.QRCode(...)`, then saves the image as a PNG under `data/`.
- The QR encoder supports two types of URLs:
  - `create_solana_pay_url(...)`: creates a real Solana Pay URL.
  - `create_solana_pay_request_url(...)`: creates a backend HTTP request URL to `/solana-pay-request`.

### What data is encoded?
- For the real Solana Pay URL, the encoded fields are:
  - `amount`
  - `reference`
  - `label`
  - `message`
  - `memo`
- The Solana Pay URL is built as:
  - `solana:<merchant_wallet>?amount=...&reference=...&label=...&message=...&memo=...`
- The backend request URL is built as:
  - `http://localhost:8000/solana-pay-request?recipient=...&amount=...&reference=...&label=...&message=...&store_id=...`

## 2. PAYMENT STRUCTURE

- Yes: `create_solana_pay_url(...)` is using Solana Pay format.
- The payment URL format is:
  - `solana:<merchant_wallet>?amount=...&reference=...&label=...&message=...&memo=...`
- Example from code:
  - `solana:<merchant_wallet>?amount=0.01&reference=<base58>&label=SolClub - <product>&message=...&memo=SolClub-<store>-<reference prefix>`

## 3. MERCHANT WALLET

- The recipient wallet is the merchant wallet stored in `data/merchant_keypair.json`.
- `SolanaPayQRGenerator.__init__()` loads or creates this merchant keypair if not provided.
- The backend in `main.py` also loads the same file and sets `MERCHANT_WALLET`.

## 4. REFERENCE / TRACKING

- A unique reference is generated by `generate_reference_key()` in `qr_wallet/qr_generator.py`.
- It creates a new temporary Solana keypair and base58-encodes its pubkey bytes.
- That `reference` is placed into the Solana Pay URL and saved into `data/transaction_metadata.json`.
- The code also adds a `memo` field like `SolClub-<store_id>-<reference prefix>`.

### Important limitation
- The backend watcher does not actually use that stored `reference` to identify the payment.
- It only scans for new transactions to the merchant wallet and processes them.

## 5. BACKEND CONNECTION

- The backend is in `main.py` inside `create_fastapi_app()`.
- A background task `transaction_watcher()` polls the Solana RPC for signatures to `MERCHANT_WALLET`.
- For each new signature it finds, it fetches the transaction, verifies it, stores it in the DB, and mints an NFT.

### How backend links to the QR
- It does not directly link the backend to a specific QR record by `reference`.
- It simply detects any new payment arriving at the merchant wallet.

## 6. LIMITATIONS

- The QR generator includes the standard fields: `reference`, `memo`, `label`, and `message`.
- But the backend does not match the transaction to QR metadata via `reference`.
- The backend watcher uses testnet RPC while QR generation uses devnet assistance, which can break detection if the transaction is actually on devnet.
- The watcher also assumes transaction balance change order and may be fragile.

## 7. FLOW

Step 1:
- Generate a Solana Pay URL in `qr_wallet/qr_generator.py`.
- Create a QR image from that URL.

Step 2:
- A user scans the QR with a Solana wallet.
- The wallet constructs and sends a payment to the merchant address.

Step 3:
- The backend watcher in `main.py` polls the merchant wallet address for new signatures.
- It fetches each new transaction, saves it, and mints NFTs.

Flow diagram (text):
- `QR generator` -> `solana:<merchant_wallet>?...` -> `wallet scan` -> `on-chain payment` -> `backend watcher polls merchant wallet` -> `detect new signature` -> `save transaction` -> `mint NFT`
